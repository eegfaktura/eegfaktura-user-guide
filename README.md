# eegFaktura — Benutzerhandbuch

End-user guide for **eegFaktura** (for EEG admins), published at
<https://eegfaktura.github.io/eegfaktura-user-guide/>. German, MkDocs Material, same style as the
eegFaktura member-onboarding user guide. Developer and architecture docs live in
[eegfaktura-docs](https://github.com/eegfaktura/eegfaktura-docs).

## Layout

| Path | Content |
|---|---|
| `docs/*.md` | chapters (numbered, in `nav` of `mkdocs.yml`) |
| `docs/images/` | screenshots, generated by `scripts/screenshots.py` — do not edit by hand |
| `docs/stylesheets/vfeeg.css` | palette (identical to the onboarding guide) |
| `docs/assets/fonts/` | Roboto / Roboto Mono, committed (no Google Fonts request), with licences |
| `scripts/screenshots.py` | Playwright script that logs in to a local eegFaktura stack and takes the screenshots |
| `scripts/screens_more.py` | the screenshot steps of the chapters Tarife to Prozesse |
| `scripts/prepare-local-stack.sql` | demo data for those chapters in the local stack |

## Preview and build

```bash
python -m venv .venv && . .venv/bin/activate
pip install --no-deps -r requirements-docs.txt
mkdocs serve            # http://localhost:8000
mkdocs build --strict   # what CI runs
```

## Screenshots

Screenshots are taken from a **local stack with fixture data only** — never from production or pilot, so no real
names, addresses or IBANs end up in the public guide. See `scripts/screenshots.py` for the stack, the login and how
to run it:

```bash
# once per local stack: demo data the tariff and billing chapters need (local stack only!)
docker exec -i eegfaktura-legacy-dev-eegfaktura-postgresql-1 psql -v ON_ERROR_STOP=1 -U postgres -d eegfaktura < scripts/prepare-local-stack.sql
pip install --no-deps -r requirements-screenshots.txt
playwright install chromium
SCREENSHOT_PASSWORD=<fixture password> python scripts/screenshots.py          # all images
SCREENSHOT_PASSWORD=<fixture password> python scripts/screenshots.py abrechnung  # only names containing this
```

The billing steps write to the local stack: a preview for the current period and, once, a final billing run for
Jul-Sep 2026 (confirmed only when the check dialog shows that period). They run in every run, also with a name filter
(the filter only selects which images are saved). Everything else only reads. A failed step leaves a debug image in `.cache/`.

## Publishing

Every merge to `main` builds the site and pushes it to the `gh-pages` branch (`.github/workflows/docs.yml`).
Pull requests only scan (Trivy, OSV-Scanner) and build (`--strict`).

## Features in the pilot zone (standard)

A feature that runs only in the pilot zone (a small number of friendly users) is documented **right away**, as it will
be in production, and marked with the shared hint `snippets/pilot.md` („Derzeit nur in der Pilot-Zone“):

- Write the text for the **final state**. Only the hint line is pilot-specific; no sentences like „in der allgemeinen
  Version …“ or „in der Pilot-Zone anders“, so nothing else has to change at the production release.
- Put the line `--8<-- "pilot.md"` (pymdownx.snippets) directly under the heading of each section that describes
  pilot behaviour, followed by a blank line. A table row cannot carry the hint: link from it to the section that does.
- „Was ist neu?“ (`docs/changelog.md`) lists the features under **„In der Pilot-Zone“**, with the hint below that
  heading.
- Screenshots stay on the production state until the production release.

**At the production release:** delete every line `--8<-- "pilot.md"` of the released features
(`grep -rn 'pilot.md' docs`), rename „In der Pilot-Zone“ in `docs/changelog.md` to the release date (move the entries
of features that stay in pilot into a new „In der Pilot-Zone“ section), update the screenshots, add a CHANGELOG
entry. Leave `snippets/pilot.md` in place for the next pilot features.

## Rules

- Versions are pinned (direct and transitive), at least 7 days old when pinned; new external sources only after
  asking. List: `EXTERNAL_SOURCES.md`.
- Every change gets an entry in `CHANGELOG.md`.
