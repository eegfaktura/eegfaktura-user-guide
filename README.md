# eegFaktura — Benutzerhandbuch

End-user guide for **eegFaktura** (for EEG admins), published at
<https://eegfaktura.github.io/eegfaktura-user-guide/>. German, MkDocs Material, same style as the
eegFaktura member-onboarding user guide. Developer and architecture docs live in
[eegfaktura-docs](https://github.com/eegfaktura/eegfaktura-docs).

## Layout

| Path | Content |
|---|---|
| `docs/*.md` | chapters (numbered, in `nav` of `mkdocs.yml`) |
| `docs/images/` | screenshots, generated by `scripts/screenshots.py` — do not edit by hand |
| `docs/stylesheets/vfeeg.css` | palette (identical to the onboarding guide) |
| `docs/assets/fonts/` | Roboto / Roboto Mono, committed (no Google Fonts request), with licences |
| `scripts/screenshots.py` | Playwright script that logs in to a local eegFaktura stack and takes the screenshots |
| `scripts/screens_more.py` | the screenshot steps of the chapters Tarife to Prozesse |
| `scripts/prepare-local-stack.sql` | demo data for those chapters in the local stack |
| `scripts/prepare-local-keycloak.sh` | optional: name and e-mail of the fixture admin in the local Keycloak (user menu) |

## Preview and build

```bash
python -m venv .venv && . .venv/bin/activate
pip install --no-deps -r requirements-docs.txt
mkdocs serve            # http://localhost:8000
mkdocs build --strict   # what CI runs
```

## Screenshots

Screenshots are taken from a **local stack with fixture data only** — never from production or pilot, so no real
names, addresses or IBANs end up in the public guide. See `scripts/screenshots.py` for the stack, the login and how
to run it:

```bash
# before every full run: demo data (community, members, tariffs) and a reset billing history (local stack only!)
docker exec -i eegfaktura-legacy-dev-eegfaktura-postgresql-1 psql -v ON_ERROR_STOP=1 -U postgres -d eegfaktura < scripts/prepare-local-stack.sql
# optional, in the WSL distribution of the stack: realistic name and e-mail of the fixture admin in the user menu
bash scripts/prepare-local-keycloak.sh
pip install --no-deps -r requirements-screenshots.txt
playwright install chromium
SCREENSHOT_PASSWORD=<fixture password> python scripts/screenshots.py          # all images
SCREENSHOT_PASSWORD=<fixture password> python scripts/screenshots.py abrechnung  # only names containing this
```

The billing steps write to the local stack: they bill the closed quarter Jul-Sep 2026 with the invoice date 05.10.2026,
preview and final run (confirmed only when the check dialog shows that period). A final run cannot be undone, so run
`prepare-local-stack.sql` before every full run; it resets the billing history of the demo community. The billing steps
run in every run, also with a name filter (the filter only selects which images are saved). Everything else only reads. A failed step leaves a debug image in `.cache/`.

## Publishing

Every merge to `main` builds the site (`--strict`) and pushes it to the `gh-pages` branch
(`.github/workflows/docs.yml`). The dependency scan (Trivy, OSV-Scanner) runs for pull requests, weekly (Monday) and
by hand; it does not hold back the deploy (08.11.2026: a scanner download outage had stopped the publishing).

## Features in the pilot zone (standard)

A feature that runs only in the pilot zone (a small number of friendly users) is documented **right away**, as it will
be in production, and marked with the shared hint `snippets/pilot.md` („Derzeit nur in der Pilot-Zone“):

- Write the text for the **final state**. Only the hint line is pilot-specific; no sentences like „in der allgemeinen
  Version …“ or „in der Pilot-Zone anders“, so nothing else has to change at the production release.
- Put the line `--8<-- "pilot.md"` (pymdownx.snippets) directly under the heading of each section that describes
  pilot behaviour, followed by a blank line. A table row cannot carry the hint: link from it to the section that does.
- „Was ist neu?“ (`docs/changelog.md`) lists the features under **„In der Pilot-Zone“**, with the hint below that
  heading, as one-line bullets in the form described under [Was ist neu?](#was-ist-neu-docschangelogmd).
- Screenshots stay on the production state until the production release.

**At the production release:** delete every line `--8<-- "pilot.md"` of the released features
(`grep -rn 'pilot.md' docs`). In `docs/changelog.md`, move the bullets of the released features from „In der
Pilot-Zone“ into the block of the current month (create it above the older months if it does not exist yet); merge a
bullet with an existing one for the same function and drop what does not meet the rule below. Features that stay in
pilot keep their bullets under „In der Pilot-Zone“; if none are left, remove that section until the next pilot feature.
Then update the screenshots and add a CHANGELOG entry. Leave `snippets/pilot.md` in place for the next pilot features.

### Was ist neu? (`docs/changelog.md`)

The page is for EEG admins, not a developer changelog:

- **One block per month** („## November 2026“), newest first, below „In der Pilot-Zone“. No heading per entry (every
  heading lands in the sidebar).
- **One line per entry**, at most about 8 per block: `- **Bereich:** was du jetzt tun kannst → [Link](kapitel.md#anker)`.
  Details belong in the chapter the link points to.
- **Only what enables a new task or changes a familiar one.** No renamings, defaults, sort orders, number formats,
  clearer messages or file names.
- **End state only:** several changes to the same function become one entry; never „zunächst …, seit … “. A merged
  entry stays in the month of the first change; later changes only update its text.
- **Age:** entries older than 6 months move into a `??? note "Ältere Änderungen"` block at the end of the page;
  delete them after 12 months.

## Rules

- Versions are pinned (direct and transitive), at least 7 days old when pinned; new external sources only after
  asking. List: `EXTERNAL_SOURCES.md`.
- Every change gets an entry in `CHANGELOG.md`.
